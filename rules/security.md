# Security rules for warehouse SQL and the execution boundary

These rules apply to every change under `src/veridelta/connectors/`, and to `models.py`, `engine.py`, and the private modules beside it that route or compile pushdown, as `applies_to` lists, on top of the root [AGENTS.md](../AGENTS.md). They matter most in `connectors/sql.py`, where every warehouse statement is assembled.

## Warehouse SQL assembly

- Assemble warehouse SQL only in `connectors/sql.py`. Do not f-string or concatenate YAML/user strings in `warehouse.py`, `engine.py`, or the private modules beside it.
- `execute_pushdown` runs compiler-produced `statement` only. Do not concatenate config fields into a second SQL string.
- Identifiers: allowlist each segment (`SQL_IDENTIFIER_SEGMENT` / `SQL_RELATION_PATTERN` in `models.py`) then dialect-quote from `_IDENTIFIER_QUOTES`, which holds an opening and a closing character (Snowflake `"`, Databricks and BigQuery backticks, T-SQL `[` and `]`). Fail closed with `ConnectorError` on disallowed characters.
- Database sources read a `table` through `compile_database_select`, which allowlists each segment and quotes it from `_DATABASE_IDENTIFIER_QUOTES`. That table is keyed by URI scheme, not `SQLDialect`, because a read needs nothing but its quote characters. A Postgres pair that sets `pushdown` compiles through `SQLDialect.POSTGRES` instead. A scheme missing from it raises `ConfigError`; never fall back to another scheme's quotes.
- `compile_database_probe`, which `veridelta validate --schemas` reads a table's columns with, only appends ` WHERE 1 = 0` to `compile_database_select`'s output. A database `query` is never wrapped or probed: it runs as written, or not at all.
- `partition_on` reaches SQL unquoted. ConnectorX writes it into each range's statement, and `compile_database_partition_counts` and `compile_database_partition_range` name it the same way, so every statement resolves the same column. The model allowlists it as one `SQL_IDENTIFIER_SEGMENT`, and the compiler checks it again before use. That allowlist is the whole control: never accept a dotted or quoted name there.
- A Postgres `table` is looked up in `pg_attribute` before it is read, so each `numeric` keeps its declared scale. `compile_postgres_columns_query` quotes the relation as the table read does and puts it inside a `'…'::regclass` literal; the allowlist admits no quote character, so the literal cannot be closed early. `compile_postgres_text_select` then names every column the catalog returned. Those names come from Postgres, not configuration, so they are quoted by doubling `"` instead of being allowlisted: doubling is the whole escape grammar of a quoted Postgres name. Never pass a configured name through that path.
- A SQL Server `table` is first read with no rows, through `compile_database_probe`, to find its `DATETIMEOFFSET` columns: the only ones ConnectorX types as a time in UTC. `compile_mssql_utc_select` then names every column that read returned, and wraps each `DATETIMEOFFSET` column in `SWITCHOFFSET(…, '+00:00')`, whose offset is a fixed literal. Those names come from SQL Server, not configuration, so they are quoted by doubling `]` instead of being allowlisted: doubling is the whole escape grammar of a bracketed SQL Server name. Never pass a configured name through that path. ConnectorX's parser undoes the doubling when it splits a read, so a partitioned read refuses any name holding `]`.
- A DuckDB source reads a `table` through `compile_duckdb_select`, which allowlists each segment and double-quotes it as the DuckDB dialect does. Its `query`, like a database `query`, is sent as written. A file opens read-only, which stops writes but not reads, and a view or macro stored in the file runs whatever its author wrote. So `_open` runs `compile_duckdb_sandbox` on every file connection before any other statement: extensions stop installing and loading on their own, files open only under the given folders, each a string literal through `_LITERAL_ESCAPES`, and the configuration locks, so no later statement can undo it. The folder is the database file's own, so a view over a file beside it still reads; inside `sandboxed`, which the MCP server opens every side in, the folders are the server's roots instead. Never open a file connection without it. `_read` refuses a `query`, before it runs, whose last statement DuckDB's parser says returns nothing or is not a kind that reads, such as an `INSERT` with `RETURNING`. That is a correctness check and not a control: a `SET` or a write that a `SELECT` follows still reaches DuckDB, where the lock, the read-only file, or the MotherDuck token refuses it. A MotherDuck connection opens read-write, since read-only needs a read-scaling token, so the docs name that token as the control. The token reaches DuckDB only in the connection `config`, never in `database` or any SQL, and the model refuses a `database` that carries one.
- Two DuckDB tables that set `pushdown` compile through `SQLDialect.DUCKDB` and run in `DuckDBPushdownSession`, which opens its connection through the same `_open` as a read, so a file stays read-only and held to its folders. It runs compiler output only. Its errors pass driver text through `mask_secrets`, and its logs name `database`, never the token.
- A database source's `query` is the user's own SQL against their own connection, sent to the driver verbatim. It is the one exception to compiler-only SQL: never concatenate anything into it, never log it, and document that a read-only role is the control. `password` is percent-encoded into the URI's user information only, never into SQL.
- Do not apply SQL identifier regex to file-source `column_names`, `primary_keys`, credentials, hostnames, tokens, database `uri`, DuckDB `database`, or lakehouse `table_uri`.
- Data literals (`value_map`, `regex_replace`, datetime formats) go through `_literal`, which applies the dialect's `_LITERAL_ESCAPES`. A `regex_replace` replacement is first rewritten from Polars' `$1` syntax into the dialect's own by `_regex_replacement`, which reads it token by token and refuses group names; `_literal` then escapes the result. Snowflake and Databricks read backslash escapes inside quotes, so both double `\` before anything else; Databricks concatenates adjacent literals, so it escapes `'` as `\'` rather than `''`. Spark replaces `${...}` in the raw statement with a session, environment, or JVM value before it parses it, so Databricks also writes `$` as the unicode escape `\u0024`, after the backslashes double; Spark decodes it inside the literal only after substitution. Do not escape by hand, and do not treat literals as identifiers. The DuckDB harness cannot see these rules; `test_sql_compiler.py` checks them against a reference lexer. BigQuery reads backslash escapes too, rejects unknown ones, and refuses a raw line break inside quotes, so its table also writes line breaks as `\n` and `\r`. T-SQL writes every literal after `N`, from `_LITERAL_PREFIXES`, so a `varchar` code page cannot lose a character. It reads a backslash before a line break as a line continuation and drops both, so `_LITERAL_REFUSALS` refuses that text with `ConfigError` rather than escape it.
- A baseline's key values reach SQL only through `_key_operand`, in `compile_changed_flags_query`: a boolean or an `int` as itself, a finite `float` through `repr`, text through `_literal`, and a date or a timestamp, as a Python value or as text for a temporal column, as a `CAST` of its ISO text through `_CAST_KEYWORDS`. Any other type raises `ConnectorError`. The row filter is a disjunction of per-row conjunctions, so a NULL key reads as `IS NULL`, never as `= NULL`, and one statement names at most `FLAGS_CHUNK` rows.
- `null_values` accepts mixed scalars, so it renders through `_sentinel_literal`: strings still go through `_literal`, while numbers and booleans emit unquoted so they cannot break a numeric column's cast. Only `str` can reach `_literal`, so the escaping guarantee is unchanged. Sentinels are also filtered against the probed dtype (`sentinels.py`) before rendering, which is a correctness control, not a security one.
- Numeric SQL operands (`absolute_tolerance`, `relative_tolerance`, `max_levenshtein_distance`, `version`, `snapshot_id`, `pad_zeros`, `partitions`) stay strict `float`/`int` fields. Do not coerce strings into SQL or Polars kwargs.
- Integer operands that are not model fields, such as a value map's `min_support`, its branch labels, and its sample cutoff, render through `_integer`, which refuses anything but a real `int`. Floats and the model's numeric fields render through `repr`, which writes `True` or a NumPy scalar as given, so never route a caller-supplied integer that way. A value map query labels columns by position, so no column name becomes a string literal, and `min_confidence` never reaches SQL at all.
- `cast_to` is a closed `CastTarget` literal rendered through `_CAST_KEYWORDS`. A type name cannot be quoted or bound inside `CAST(x AS ...)`, so the table is the whole control. Never interpolate the config value directly, and never widen the literal without adding a keyword for every dialect.
- `datetime_format` is translated one token at a time against `_STRPTIME_DIRECTIVES`, with literal runs restricted to `_FORMAT_LITERALS` and wrapped in the dialect's quoting. The allowlist excludes both quote characters, so no literal run can close its own quoting. Do not replace this with a regex substitution pass, which cannot tell a directive from literal text and leaves unrecognized input in the emitted format.
- Redshift reads backslash escapes inside string literals, so its `_LITERAL_ESCAPES` double `\` before anything else, as Snowflake's do, and its session checks a literal with a backslash before any statement. Its `REGEXP_REPLACE` documents no syntax for a group or an escape in the replacement, so `_PLAIN_REPLACEMENTS` refuses a replacement holding a group reference, `$`, or a backslash rather than guess.
- A SQL Server or Redshift pushdown session checks the server before any statement with the statements `compile_tsql_server_checks` and `compile_redshift_server_check` write, from a fixed probe text through `_string_literal` and the dialect's own tables. No configuration value reaches them.
- A dialect whose `=` is not Polars' equality on text compares text through `_EXACT_TEXT`. T-SQL's default collation ignores case and accents, and its `=` ignores trailing spaces, so every text join, comparison, sentinel, map key, and grouping there names a binary collation and appends a sentinel character. This is a correctness control, not a security one: the operand is compiler output, never configuration.
- Do not add sanitization libraries. Quoting plus allowlists plus strict types is the control.

## Execution boundary

- Drivers receive compiled SQL or native scan kwargs. Never interpolate passwords, tokens, or URIs into SQL.
- Pattern-only `DiffRule` values stay rejected at compile time.
- Every dialect-specific keyword, quote character, or function name belongs in a module-scope table in `sql.py` keyed by `SQLDialect`, so a missing entry raises instead of inheriting another dialect's syntax. Where dialects differ structurally rather than by a token, name every dialect explicitly in the branch.
- `veridelta run` runs `git rev-parse HEAD` and `git status --porcelain --untracked-files=no` in the working folder for the run record, through `_git` in `_provenance.py`: fixed arguments, no shell, a timeout, and stdin closed. Both calls pass `safe.bareRepository=explicit` and `core.fsmonitor=false`, and status runs with `--no-optional-locks`, so neither call runs a hook. With git 2.38 or later, committed files shaped like a bare repository cannot name the commit. Older git ignores the setting. Git still reads the repository's own `.git/config` and `.gitattributes`, so a clean filter that `.git/config` defines and `.gitattributes` selects runs as the user. Running `veridelta run` inside a checkout or a delivered folder that carries its own `.git` trusts that folder's git configuration. `veridelta mcp` collects no record, so an agent's roots never start git. Any failure leaves the field null. The CI run's URL is built only from GitHub's variables in the shapes `_ci_run_url` allows, and `RunProvenance` refuses any URL that could break out of a Markdown link or an `href`.
- An Iceberg table is loaded by `_static_table` in `connectors/lakehouse.py`, never by Polars or `StaticTable.from_metadata` from a path, and never through a catalog. Both build the table's FileIO from its metadata properties too. PyIceberg imports the class a property such as `py-io-impl` or `s3.retry-strategy-impl` names, so whoever writes a table would choose code to run. `names_a_pyiceberg_class` in `models.py` matches every such key: one that starts with `py-` or ends with `impl`. `_static_table` builds the FileIO from `storage_options` alone, drops every such property from the metadata, and hands the table to `pl.scan_iceberg`. `IcebergConfig` refuses such a `storage_options` key, naming the key but never its value. It also refuses a `table_uri` with no slash, which Polars would look up in a catalog, as [the decision](../decisions/iceberg-tables-load-from-a-path.md) records. Never pickle the scan: Polars reloads a pickled table from its path.
- Inside `checking_table_files`, which the MCP server opens around every read, `_static_table` builds the FileIO with `checked_file_io`, and the scan passes `reader_override="pyiceberg"`. PyIceberg then plans the scan and opens every file through that one FileIO: the version hint, the metadata file, the manifest lists, the manifests, and the data and delete files. The FileIO hands the server's check the path PyArrow opens on this machine, or the URI of a file elsewhere, from its own `parse_location`, just before it opens it. Never let Polars plan or read such a scan: the `polars_iceberg` plugin and Polars' own reader parse a location otherwise than PyIceberg, so they could open a file no check saw, and Polars' cache of metadata files could serve bytes no check read. A FileIO class of Veridelta's own keeps the plugin and that cache away. The MCP server lists a table's files through the same FileIO. It opens a file only through a scheme in `_CHECKED_SCHEMES`: `file`, whose path it checks, and the object stores', whose host it checks. Never add `hdfs` or `viewfs`: PyArrow opens them through libhdfs, which it can load from the working directory, the server's first root, so a table that names one would run a library an agent wrote there.
- Inside `checking_table_files`, a Delta Lake scan calls the server's `_checked_delta_table`, which walks the log of a table on this machine, loads one `DeltaTable`, and lists and checks each data file and each deletion vector's file of that version. The scan reads that `DeltaTable` and no other. `_checked_delta_scan` reads the data files through deltalake's own fragments, in a PyArrow `PyFileSystem` whose handler opens only the files the version lists, each checked just before it opens: a file of a table under any scheme in `_DELTA_LOCAL_SCHEMES` (`file`, `fs`, and `opendal+fs`, which deltalake reads from this machine) at the path `file_uris` names, or the path of the URI it names, which the handler opens itself, and a file elsewhere by its URI, which deltalake's store opens. Never hand such a table to `pl.scan_delta` to read: Polars reads the data files in Rust, where no check runs. deltalake reads the log, as it loads the `DeltaTable`, and the deletion vectors, in `deletion_vectors`, in Rust too, each right after the check of its files. A file swapped in that moment is read as swapped: that window remains. A checkpoint can name a sidecar anywhere, which deltalake reads as it loads the `DeltaTable`, whatever the table's protocol says, and reports nowhere. So `delta_log_vectors` reads the log before the `DeltaTable` is loaded, and refuses a table whose log records a `sidecar` action: never load a `DeltaTable` on the server before that read. That read is apart from the `DeltaTable`'s own, so a log swapped between the two can have deltalake read a sidecar or a vector whose file was never checked. The scan drops the rows each vector deletes as Polars' own scan does, and reads a text partition's value of `''` from the file's folder, as Polars does where deltalake reads null, so it returns the rows `veridelta run` returns.
- deltalake reports no deletion vector's file, so `delta_log_vectors` reads every commit and checkpoint in the log, and `deletion_vector_files` names the file of each vector an `add` action records, at any version. A log on this machine is read from the files the walk checked, and only a table on another machine through deltalake's storage, which can crash the process as it lists a folder on this machine. Delta Lake joins the folder of a vector at a relative path to the table's URI as a URL, so a folder of other characters than letters and digits is refused, since a `/`, a `..`, or a scheme in it could lead anywhere. deltalake parses a table URI as the URL standard says, which removes each `.` and `..` segment by its text, `%2e` included, where the walk reads the folder the system finds, through links and only where folders exist. So `_table_files` refuses a Delta Lake `table_uri` with a scheme whose text, with every `%` escape decoded, holds such a segment, before the walk or deltalake reads anything. deltalake decodes the path of an `fs:` or `opendal+fs:` URI twice, where the walk and `file_uris` decode it once, so `_table_files` refuses such a `table_uri` with any `%` in it. deltalake expands only `~` and `~/`, and reads `~alice/t` as a folder of that name, so `_delta_files` hands deltalake the path the walk expanded. Otherwise deltalake and the walk both read a path with no scheme as the system does.
- `veridelta run` runs `git rev-parse HEAD` and `git status --porcelain --untracked-files=no` in the working folder for the run record, through `_git` in `_provenance.py`: fixed arguments, no shell, a timeout, and stdin closed. The folder's `.git` belongs to whoever runs the command, and `veridelta mcp` collects no record, so an agent's roots never start git. Any failure leaves the field null. The CI run's URL is built only from GitHub's variables in the shapes `_ci_run_url` allows, and `RunProvenance` refuses any URL that could break out of a Markdown link or an `href`.
- `veridelta mcp` connects a side only to the hosts its operator gives with `--allow-host`, and `_destinations` in `mcp_server.py` names each host a side's configuration chooses. A new source type, or a setting that changes where a connector connects, names its host there too, or None when the server cannot check it. A `storage_options` key reaches a reader only when `_option_hosts` knows it. A location's scheme is exempt from the host check only in `_LOCAL_SCHEMES`, whose path is checked under the roots, or `_SERVICE_SCHEMES`; never add a list of remote schemes, which misses whatever a reader adds. A connection string's own options, such as a MotherDuck `database`'s, pass only from a list of options known to choose no host, and the rest of the string only as characters that hold no option, since a driver can find an option after a separator the server does not split on. A DuckDB `database` that DuckDB opens through an extension is refused. A database `uri` is read as ConnectorX reads it, through `connectorx_url` in `connectors/database.py`, which also models the rewrite of ConnectorX's Python package that sends a scheme holding `redshift` and not `-iam`, such as `sqliteredshift`, to its Postgres reader, and a test compares it with the installed ConnectorX's `rewrite_conn`. `_refuse_database_uri` refuses a reader that signs in where no check sees, BigQuery's key file and Redshift IAM's AWS sign-in, a parameter in `_FILE_PARAMETERS` that names a TLS file the driver opens, and an Oracle `alias` or an Oracle path outside `_ORACLE_PATH`, since ConnectorX writes the path into the connect string. `_database_hosts` skips only a URI ConnectorX reads as SQLite, whose file `check_data_paths` checks, never a scheme that merely starts with `sqlite`. It checks a Trino URI decoded, with the `password` field in it, since ConnectorX decodes it whole before it finds the host, and splits the decoded text without `urlsplit`, which raises on an unmatched bracket. A ConnectorX option that opens a file on this machine or chooses a sign-in host joins one of those checks. A host is read only from text in `_HOST_AND_PORT`'s shape, never as a part of other text, such as the text after an `@`, since readers split a login, a `%`, or a `\` in different places: the text comes back whole, and `_refuse_hosts` refuses it. Match a scheme or a prefix in ASCII only, with no `str.lower` on text outside ASCII and no `re.IGNORECASE` without `re.ASCII`, since the Kelvin sign lowers to `k`. Call `_refuse_hosts` before `check_data_paths`, which lists a Delta Lake or Iceberg table's files and so connects to the table's host. Otherwise a configuration an agent writes can send a `${NAME}` value to any host, or reach one on the server's network. `_refuse_listed` holds each file a table's log or metadata names to the same allowed hosts, through `_location_hosts` and `_refuse_host`, and so does `_refuse_opened` for each file a checked scan opens elsewhere. Such a file's URI is read in `_NAMED_FILE`'s shape, which allows an `@` after the authority, as a partition value can hold one: only the authority, up to its first `/`, chooses the host for deltalake's store and PyIceberg's FileIO, and it is still held to `_HOST_AND_PORT`. Their messages leave the location out, since a file named it.
- On Windows, resolving, matching, or opening a path that starts with two separators of either kind, such as `\\host\share` or `\\?\UNC\host\share`, or with `\??\`, reaches the machine or the device it names, and can send the user's credentials there. `names_another_machine` in `connectors/base.py` says, from the text alone, whether the system reads a path that way; on Linux and macOS, nothing counts, and Cygwin and MSYS count as Windows. Ask it before every `realpath`, `resolve`, `glob`, or `stat` of a path an agent can choose: `resolve_path`'s, each data location, Snowflake's key file, and the files a table lists in `check_data_paths`, and `sqlite_path`'s, which returns such a path decoded but not resolved, so the MCP server refuses it as written. Ask it about the text as written, before `Path` reads it: on Python 3.11, Windows' `Path` drops a separator from `//host` or `\\\host\share`, and the result reads as a path on this machine, so `_opened_inside` and `_refuse_opened` ask it first. `_local_paths` refuses a `file:` URI that names a host other than `localhost`, in either way of parsing it, since deltalake opens it on that host on Windows. It refuses a local scheme's URI whose path starts with `//`, in either way of parsing it, before `url2pathname` converts it: Python 3.14 drops `localhost` or the machine's own name there, so `file:////localhost/x` converts to `/x` while DuckDB opens `/localhost/x`. It also refuses a URI whose path `url2pathname` cannot convert, as Windows before 3.14 cannot one with a second `:`, so catch every error it raises: `OSError`, which `URLError` is, `ValueError`, and `IndexError`. Each fails with a `ConfigError` that names the setting and never the value, since a table's files can hold it.
- A setting that names a file a connector opens on this machine, such as a key or a certificate, is a path an agent can choose too. `veridelta mcp` either holds it to the roots in `check_data_paths`, by the rules a data path follows, as `_refuse_key_file` holds Snowflake's `private_key_path`, or refuses it outright, as `_destinations` refuses a BigQuery `credentials_path`, whose file names the host its sign-in goes to, and `_refuse_database_uri` refuses a database `uri` parameter in `_FILE_PARAMETERS`. A new source type, or a setting that names such a file, does one or the other before anything opens the file.
- `DiffResult.rules_applied` describes each column's rules through `rules_applied` in `_resolution.py`, as settings and counts. A value map's entries, a regex's text, and null sentinels never reach it, since they can hold data or describe its shape, and the HTML report reads only it. `tests/unit/test_report.py` holds both to that with a marker string.
- A `ConnectorError` whose message quotes a reader's or a driver's own text sets `quotes_data`, since that text can hold a cell, and `veridelta mcp` leaves such a message out unless started with `--allow-row-values`, as it does any message that is not a `VerideltaError`'s, in a failed call and in a `validate_config` finding. A `cast_to` that meets a value it cannot convert raises a `DataIntegrityError` that counts the values and never quotes them.
- Treat configuration, input files, CLI arguments, and external data as untrusted input. Validate at the boundary and do not bypass validated models with `model_construct` except in tests or explicitly documented internal paths.
