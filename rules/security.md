# Security rules for warehouse SQL and the execution boundary

These rules apply to every change under `src/veridelta/connectors/`, and to `models.py`, `engine.py`, and the private modules beside it that route or compile pushdown, as `applies_to` lists, on top of the root [AGENTS.md](../AGENTS.md). They matter most in `connectors/sql.py`, where every warehouse statement is assembled.

## Warehouse SQL assembly

- Assemble warehouse SQL only in `connectors/sql.py`. Do not f-string or concatenate YAML/user strings in `warehouse.py`, `engine.py`, or the private modules beside it.
- `execute_pushdown` runs compiler-produced `statement` only. Do not concatenate config fields into a second SQL string.
- Identifiers: allowlist each segment (`SQL_IDENTIFIER_SEGMENT` / `SQL_RELATION_PATTERN` in `models.py`) then dialect-quote (Snowflake `"`, Databricks and BigQuery backticks). Fail closed with `ConnectorError` on disallowed characters.
- Database sources read a `table` through `compile_database_select`, which allowlists each segment and quotes it from `_DATABASE_IDENTIFIER_QUOTES`. That table is keyed by URI scheme, not `SQLDialect`, because a read needs nothing but its quote characters. A Postgres pair that sets `pushdown` compiles through `SQLDialect.POSTGRES` instead. A scheme missing from it raises `ConfigError`; never fall back to another scheme's quotes.
- `compile_database_probe`, which `veridelta validate --schemas` reads a table's columns with, only appends ` WHERE 1 = 0` to `compile_database_select`'s output. A database `query` is never wrapped or probed: it runs as written, or not at all.
- `partition_on` reaches SQL unquoted. ConnectorX writes it into each range's statement, and `compile_database_partition_counts` and `compile_database_partition_range` name it the same way, so every statement resolves the same column. The model allowlists it as one `SQL_IDENTIFIER_SEGMENT`, and the compiler checks it again before use. That allowlist is the whole control: never accept a dotted or quoted name there.
- A Postgres `table` is looked up in `pg_attribute` before it is read, so each `numeric` keeps its declared scale. `compile_postgres_columns_query` quotes the relation as the table read does and puts it inside a `'…'::regclass` literal; the allowlist admits no quote character, so the literal cannot be closed early. `compile_postgres_text_select` then names every column the catalog returned. Those names come from Postgres, not configuration, so they are quoted by doubling `"` instead of being allowlisted: doubling is the whole escape grammar of a quoted Postgres name. Never pass a configured name through that path.
- A SQL Server `table` is first read with no rows, through `compile_database_probe`, to find its `DATETIMEOFFSET` columns: the only ones ConnectorX types as a time in UTC. `compile_mssql_utc_select` then names every column that read returned, and wraps each `DATETIMEOFFSET` column in `SWITCHOFFSET(…, '+00:00')`, whose offset is a fixed literal. Those names come from SQL Server, not configuration, so they are quoted by doubling `]` instead of being allowlisted: doubling is the whole escape grammar of a bracketed SQL Server name. Never pass a configured name through that path. ConnectorX's parser undoes the doubling when it splits a read, so a partitioned read refuses any name holding `]`.
- A DuckDB source reads a `table` through `compile_duckdb_select`, which allowlists each segment and double-quotes it as the DuckDB dialect does. Its `query`, like a database `query`, is sent as written. A file opens read-only, which is the control there. Inside `sandboxed`, which the MCP server opens every side in, `_open` then runs `compile_duckdb_sandbox`: extensions stop loading on their own, files open only under the given folders, each a string literal through `_LITERAL_ESCAPES`, and the configuration locks, so no later statement can undo it. A MotherDuck connection opens read-write, since read-only needs a read-scaling token, so the docs name that token as the control. The token reaches DuckDB only in the connection `config`, never in `database` or any SQL, and the model refuses a `database` that carries one.
- Two DuckDB tables that set `pushdown` compile through `SQLDialect.DUCKDB` and run in `DuckDBPushdownSession`, which opens its connection through the same `_open` as a read, so a file stays read-only. It runs compiler output only. Its errors pass driver text through `mask_secrets`, and its logs name `database`, never the token.
- A database source's `query` is the user's own SQL against their own connection, sent to the driver verbatim. It is the one exception to compiler-only SQL: never concatenate anything into it, never log it, and document that a read-only role is the control. `password` is percent-encoded into the URI's user information only, never into SQL.
- Do not apply SQL identifier regex to file-source `column_names`, `primary_keys`, credentials, hostnames, tokens, database `uri`, DuckDB `database`, or lakehouse `table_uri`.
- Data literals (`value_map`, `regex_replace`, datetime formats) go through `_literal`, which applies the dialect's `_LITERAL_ESCAPES`. A `regex_replace` replacement is first rewritten from Polars' `$1` syntax into the dialect's own by `_regex_replacement`, which reads it token by token and refuses group names; `_literal` then escapes the result. Snowflake and Databricks read backslash escapes inside quotes, so both double `\` before anything else; Databricks concatenates adjacent literals, so it escapes `'` as `\'` rather than `''`. Do not escape by hand, and do not treat literals as identifiers. The DuckDB harness cannot see these rules; `test_sql_compiler.py` checks them against a reference lexer. BigQuery reads backslash escapes too, rejects unknown ones, and refuses a raw line break inside quotes, so its table also writes line breaks as `\n` and `\r`.
- `null_values` accepts mixed scalars, so it renders through `_sentinel_literal`: strings still go through `_literal`, while numbers and booleans emit unquoted so they cannot break a numeric column's cast. Only `str` can reach `_literal`, so the escaping guarantee is unchanged. Sentinels are also filtered against the probed dtype (`sentinels.py`) before rendering, which is a correctness control, not a security one.
- Numeric SQL operands (`absolute_tolerance`, `relative_tolerance`, `max_levenshtein_distance`, `version`, `snapshot_id`, `pad_zeros`, `partitions`) stay strict `float`/`int` fields. Do not coerce strings into SQL or Polars kwargs.
- Integer operands that are not model fields, such as a value map's `min_support`, its branch labels, and its sample cutoff, render through `_integer`, which refuses anything but a real `int`. Floats and the model's numeric fields render through `repr`, which writes `True` or a NumPy scalar as given, so never route a caller-supplied integer that way. A value map query labels columns by position, so no column name becomes a string literal, and `min_confidence` never reaches SQL at all.
- `cast_to` is a closed `CastTarget` literal rendered through `_CAST_KEYWORDS`. A type name cannot be quoted or bound inside `CAST(x AS ...)`, so the table is the whole control. Never interpolate the config value directly, and never widen the literal without adding a keyword for every dialect.
- `datetime_format` is translated one token at a time against `_STRPTIME_DIRECTIVES`, with literal runs restricted to `_FORMAT_LITERALS` and wrapped in the dialect's quoting. The allowlist excludes both quote characters, so no literal run can close its own quoting. Do not replace this with a regex substitution pass, which cannot tell a directive from literal text and leaves unrecognized input in the emitted format.
- Do not add sanitization libraries. Quoting plus allowlists plus strict types is the control.

## Execution boundary

- Drivers receive compiled SQL or native scan kwargs. Never interpolate passwords, tokens, or URIs into SQL.
- Pattern-only `DiffRule` values stay rejected at compile time.
- Every dialect-specific keyword, quote character, or function name belongs in a module-scope table in `sql.py` keyed by `SQLDialect`, so a missing entry raises instead of inheriting another dialect's syntax. Where dialects differ structurally rather than by a token, name every dialect explicitly in the branch.
- Treat configuration, input files, CLI arguments, and external data as untrusted input. Validate at the boundary and do not bypass validated models with `model_construct` except in tests or explicitly documented internal paths.
