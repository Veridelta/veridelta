**Claim:** On `veridelta mcp`, a `${NAME}` in a database `password`, a Snowflake `password`, or a Snowflake `private_key_passphrase` keeps taking any text in UTF-8 of 4 or more characters. The one exception is a ClickHouse `password`, which takes only letters, digits, and `! $ % & ' ( ) * + , . _ ~ -`, as [the record of its password](clickhouse-password-goes-in-unencoded.md) says. The mask keeps matching a value only as written and in its encodings, never with its quotes doubled, its backslashes escaped, as JSON, inside ODBC braces, as base64, or cut. That is safe only while no reader writes a password in such a form. So `_load_checked` takes a `${NAME}` in a database side, in `password` or as the uri's user or password, only when `connectorx_url` names a reader in `_PASSWORD_READERS`: PostgreSQL and Redshift, MySQL, SQL Server, Oracle, and ClickHouse. Trino is left out. A uri user is refused there too. Trino's reader sends it beside a password in the file as basic auth, so any variable with a user's shape would come back in base64. `tests/integration/test_mcp_password_echo.py` and `tests/integration/test_mcp_password_servers.py` pin the claim for each of them, and for Snowflake, whose connector is the only reader of its password and passphrase.

**Evidence:** Through the MCP client, `test_mcp_password_servers.py` signed in to a local PostgreSQL 16 under `scram-sha-256`, `md5`, and `password` (clear text) with three wrong passwords of every character class, through `validate_config` with schemas. No answer held a run of 4 characters of the password, or any escaped form of it, and the server log showed 21 failed sign-ins for each method. `test_mcp_password_echo.py` drives fakes of PostgreSQL, MySQL, SQL Server, ClickHouse, and Snowflake, with Oracle and a Snowflake key's passphrase, through `validate_config`, `describe_schema`, and `run_comparison`: 108 answers, none with a piece of the password. The ClickHouse fakes are also driven with a password of every character ClickHouse takes. The connector refuses each password of every kind of character before it reaches them. The Postgres fake asks for the password in clear text and receives it whole. ConnectorX reports `password authentication failed for user "u"`, ERR 1045 with the user, `Timed out in bb8`, `DPI-1047`, and Snowflake's `390100` text. Its ClickHouse reader repeats the whole body of a refusal. So a second ClickHouse fake writes its whole request back, as an echo or debug endpoint on an allowed host would, and the answer shows `x-clickhouse-key: ***`: the header holds the password as written, as the mask matches it. The Trino reader repeats the whole body of a refusal too, as `http not ok, code: 401 Unauthorized, reason:` and the body. It sends the user and the password as basic auth, in base64, to whatever host and port the uri names. `test_the_trino_reader_repeats_a_password_a_service_writes_back` has an HTTPS fake write its request headers back, and the answer holds the base64 of the user and the password, unmasked. So Trino is not in the list. The Snowflake driver sends a password only to the account's host under `snowflakecomputing.com`, which no agent can point elsewhere, so its fake has no echoing variant. tokio-postgres leaves the login out of its parse errors, such as `parse error: invalid port number`, and a model error names the setting, never its value. The control in the same file has the fake write the password back in 15 escaped forms: each comes back unmasked and is found, and the raw form comes back as `***`. The evidence has limits. Oracle is probed only up to DPI-1047, since CI has no Oracle Client. Snowflake is driven by a fake only. The corpus pins the driver versions in the lockfile. A server that speaks a reader's own protocol and asks for the password in clear text could write it back escaped, as the control shows, but such a server holds the password already.

**Alternative considered:** Give every secret slot `_UNRESERVED`'s shape, letters, digits, `.`, `_`, `~`, and `-`, as a uri password has. A second alternative adds each escaped form of a recorded value to `_mask_pattern`: quotes doubled, backslashes escaped, JSON, ODBC braces, libpq quoting, and the base64 Trino sends.

**Why rejected:** The shape refuses common real passwords and passphrases, such as the defaults of RDS and Secrets Manager, Azure SQL's rules, Snowflake's, and any with a letter outside ASCII, to stop an echo that no reader in the list produces. It would also break the remedy for a uri password with other characters, which moves it to the `password` setting, and would not stop Trino's base64, which changes even a password of letters. Escaped forms are a list with no source to check it against, they grow the pattern for every value, and none of them matches a cut. Trino decodes and re-encodes a password before it sends one, so the base64 is not that of the value the server expanded. The record that the MCP server takes a `${NAME}` only in a credential setting rejects piece masking too.

**How to reverse:** To drop the list of readers, remove `_PASSWORD_READERS` and its branch in `_load_checked` in `src/veridelta/mcp_server.py`, the tests of it in `TestEnvironmentReferences`, and the sentences about it in `docs/agents.md` and the 0.43.0 section of `docs/upgrading.md`. That lets Trino's base64 through again. To move to a shape instead, add a branch for the `secret` slot to `_shape_needed` with `_UNRESERVED`, keep Trino out of the list, and list the refused passwords in `docs/upgrading.md`.
