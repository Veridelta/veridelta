**Claim:** For a Delta Lake table that deltalake reads from this machine, `_delta_files` in `src/veridelta/mcp_server.py` copies `_last_checkpoint`, each file of the log that deltalake reads for the version it loads, from the latest complete checkpoint at or before that version on, or from an earlier checkpoint that `_last_checkpoint` names, and each deletion vector at a relative path, just after its check, into a `DeltaLogCopy` in the system's temporary folder, and loads the `DeltaTable` from that copy. Each copy lies at a path the server builds in that folder, never at one the log names, and the copy holds at most 10,000 files and folders and takes at most 1 GiB, each file counting its bytes and one block of the folder's file system, and each folder one block. It refuses the table when that folder lies under a root, when the folder's path holds a `%`, or a `\` outside Windows, which deltalake reads as other text, when a name in the log holds a `\` outside Windows, when the copy would pass either limit, and when the log stores a deletion vector at its own path, which deltalake reads where the log says.

**Evidence:** deltalake 1.6 reads the log again in Rust as it builds a `DeltaTable`, and each vector's file in `deletion_vectors`. On origin/main, a commit written after the server read the log, naming a vector outside the roots, chose which rows a scan returned. A copy that took a vector's path from the log wrote a file the log chose outside every root. A copy of every file in the log, whatever its name, let a sparse file or a dozen links to one file under a root, which take no room there, write gigabytes into the temporary folder on each listing, where deltalake reads none of them. A limit on the bytes alone let 60,000 hard links named as commits to one empty file under a root make 60,000 files in the temporary folder, and a limit on bytes and files with each file counting a block holds that to 10,000. With strace, deltalake 1.6.6 and 0.15.0 open only `_last_checkpoint`, the latest checkpoint at or before the version, and the commits after it. deltalake 1.6.6 starts at the latest complete checkpoint even when `_last_checkpoint` names an earlier one, and 0.15.0 starts at the one `_last_checkpoint` names, failing when that checkpoint is missing, so the copy starts at the earlier of the two. deltalake also reads a `\` in a name it lists as `/`, and resolves a `..`, so such a name, copied, led it to a commit outside the copy that no check saw. deltalake decodes a `%` escape in the copy's path and, outside Windows, reads a `\` there as `/`, so with such a temporary folder it loaded the log of another folder, which anyone who could write there chose, while its `table_uri` still named the copy. So only the folder's path can show it, before the load. `test_it_loads_a_delta_table_from_the_log_it_checked`, `test_it_refuses_a_file_replaced_as_it_is_checked`, `test_it_refuses_a_file_swapped_in_for_its_open_alone`, `test_it_writes_no_copy_through_a_link_in_its_folder`, `test_it_copies_no_log_into_a_folder_whose_path_holds_a_backslash`, `test_it_copies_only_the_files_of_a_delta_log_that_deltalake_reads`, `test_it_copies_a_delta_log_from_the_checkpoint_deltalake_starts_at`, `test_it_starts_a_delta_log_copy_at_a_checkpoint_only_once_each_part_is_there`, `test_it_refuses_a_delta_log_larger_than_it_copies`, `test_it_refuses_a_name_in_a_delta_log_that_holds_a_backslash`, and `test_it_refuses_a_delta_table_on_this_machine_with_a_vector_at_its_own_path` in `tests/unit/test_mcp_server.py` hold the copy to that. `test_the_server_reads_the_rows_polars_reads` in `tests/integration/test_lakehouse_sources.py` holds its rows to `pl.scan_delta`'s, with checkpoints, deletion vectors in the table's folder, partitions, and a new column, and `test_the_server_refuses_a_table_with_a_vector_at_its_own_path` holds the refusal.

**Alternative considered:** Load the table from its own folder, then compare the version, the actions, and the device and number of each log and vector file deltalake read with those the server checked, and refuse a scan whose files differ.

**Why rejected:** deltalake reports neither the files it read nor a vector's descriptor, so the comparison would rest on stats taken around its read. A file swapped in for that read and swapped back would pass. The copy leaves deltalake no file in the table's folder to read, and costs a copy of the files deltalake reads, up to 10,000 files and folders and 1 GiB, for each listing. A larger copy is refused, not made, so a table with large checkpoints, or with more than about 10,000 commits, checksums, and vectors after its latest checkpoint, needs `veridelta run`. The copy itself compares the file it opens with the file its path named before the check, so two swaps that bracket the check still get through. Checking the path of the open file would close that, but Linux, macOS, and Windows each give it through a call of their own, so the comparison stays. A vector at its own path is the one file the copy cannot hold, since deltalake reads it where the log says: the copy could hold it only by writing at a path the log names, which let a log choose a file to write outside the roots, or by rewriting the log. Comparing its stats around deltalake's read, as this alternative does, let two swaps through and refused legitimate tables where a stat failed. So the server refuses such a table, and `veridelta run` reads it. Writers store a vector in the table's folder by default, so the refusal reaches few tables.

**How to reverse:** In `_delta_files`, set `copy` to None for every table, which loads the table from its own folder as before, and delete `DeltaLogCopy`, `_copy_checked`, the refusal of a `p` vector, and the copy's paragraph in `rules/security.md` and `docs/agents.md`.
