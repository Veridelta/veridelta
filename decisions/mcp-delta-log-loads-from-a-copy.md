**Claim:** For a Delta Lake table that deltalake reads from this machine, `_delta_files` in `src/veridelta/mcp_server.py` copies each file of the log, and each deletion vector at a relative path, just after its check, into a `DeltaLogCopy` in the system's temporary folder, and loads the `DeltaTable` from that copy. Each copy lies at a path the server builds in that folder, never at one the log names. It refuses the table when that folder lies under a root, when the folder's path holds a `%`, or a `\` outside Windows, which deltalake reads as other text, and when the log stores a deletion vector at its own path, which deltalake reads where the log says.

**Evidence:** deltalake 1.6 reads the log again in Rust as it builds a `DeltaTable`, and each vector's file in `deletion_vectors`. On origin/main, a commit written after the server read the log, naming a vector outside the roots, chose which rows a scan returned. A copy that took a vector's path from the log wrote a file the log chose outside every root. deltalake decodes a `%` escape in the copy's path and, outside Windows, reads a `\` there as `/`, so with such a temporary folder it loaded the log of another folder, which anyone who could write there chose, while its `table_uri` still named the copy. So only the folder's path can show it, before the load. `test_it_loads_a_delta_table_from_the_log_it_checked`, `test_it_refuses_a_file_replaced_as_it_is_checked`, `test_it_refuses_a_file_swapped_in_for_its_open_alone`, `test_it_writes_no_copy_through_a_link_in_its_folder`, `test_it_copies_no_log_into_a_folder_whose_path_holds_a_backslash`, and `test_it_refuses_a_delta_table_on_this_machine_with_a_vector_at_its_own_path` in `tests/unit/test_mcp_server.py` hold the copy to that. `test_the_server_reads_the_rows_polars_reads` in `tests/integration/test_lakehouse_sources.py` holds its rows to `pl.scan_delta`'s, with checkpoints, deletion vectors in the table's folder, partitions, and a new column, and `test_the_server_refuses_a_table_with_a_vector_at_its_own_path` holds the refusal.

**Alternative considered:** Load the table from its own folder, then compare the version, the actions, and the device and number of each log and vector file deltalake read with those the server checked, and refuse a scan whose files differ.

**Why rejected:** deltalake reports neither the files it read nor a vector's descriptor, so the comparison would rest on stats taken around its read. A file swapped in for that read and swapped back would pass. The copy leaves deltalake no file in the table's folder to read, and costs one copy of the log for each listing. The copy itself compares the file it opens with the file its path named before the check, so two swaps that bracket the check still get through. Checking the path of the open file would close that, but Linux, macOS, and Windows each give it through a call of their own, so the comparison stays. A vector at its own path is the one file the copy cannot hold, since deltalake reads it where the log says: the copy could hold it only by writing at a path the log names, which let a log choose a file to write outside the roots, or by rewriting the log. Comparing its stats around deltalake's read, as this alternative does, let two swaps through and refused legitimate tables where a stat failed. So the server refuses such a table, and `veridelta run` reads it. Writers store a vector in the table's folder by default, so the refusal reaches few tables.

**How to reverse:** In `_delta_files`, set `copy` to None for every table, which loads the table from its own folder as before, and delete `DeltaLogCopy`, `_copy_checked`, the refusal of a `p` vector, and the copy's paragraph in `rules/security.md` and `docs/agents.md`.
