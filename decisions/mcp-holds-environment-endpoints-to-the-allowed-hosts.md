**Claim:** On `veridelta mcp`, whenever a tool opens a side, the server checks the endpoints a reader of that side's store would take from its process environment. These are the variables in `_ENVIRONMENT_ENDPOINTS`, the `endpoint_url` of the AWS profile the environment selects, and the `gcs_base_url` of a Google service account key the environment gives. They also include the Azure emulator switch, the switches that turn off a certificate check, and MotherDuck's settings. Each endpoint must meet the three rules a `storage_options` endpoint meets. Its host is given with `--allow-host` and written in `_HOST_AND_PORT`'s shape. Nothing follows the host and port but a single `/`. A value with a scheme starts with `https://`, in lowercase, on this machine too. A region a reader writes into an S3 host, from `AWS_REGION`, `AWS_DEFAULT_REGION`, or the profile's `region`, must be letters, digits, and hyphens, as a region storage option must. The Azure account `AZURE_STORAGE_ACCOUNT_NAME` names must be given with `--allow-host`, as an `azure_storage_account_name` must. A name that only deltalake reads, such as `ENDPOINT`, `ENDPOINT_URL`, `AWS_S3_ENDPOINT`, `ALLOW_INVALID_CERTIFICATES`, `REGION`, or `DEFAULT_REGION`, is checked on a Delta Lake side only. Every other name is checked on each side of its store, an Iceberg side counting as one of every object store. The check runs whether or not the configuration names its own endpoint, which is simpler and only stricter. The server still starts, and the refusal is a `ConfigError` for that call, which names the variable as it is set and never its value. Nothing is recorded or masked, since an endpoint is no credential. Sign-in and metadata endpoints, which receive only the environment's own credentials, and proxies are left to the operator.

**Evidence:** Through the MCP client on origin/main, a side that named only `s3://lake/a.parquet` read from a plain-HTTP store that `AWS_ENDPOINT_URL` named, and signed the request. A profile's `endpoint_url` received the keys a `${NAME}` gave in `storage_options`. `AZURE_AUTHORITY_HOST` received a client secret from the configuration's `${NAME}` in clear. Probes of Polars 1.39.3 and 2.1.0 and deltalake 1.6.6 against a counting store found each variable in `_ENVIRONMENT_ENDPOINTS`, whose docstring names each reader. `AZURE_STORAGE_USE_EMULATOR` replaced even a checked `azure_storage_endpoint`. A read of an `http` or `https` location, even at an S3, Azure, or Google Cloud Storage host, sent nothing to any of these endpoints on either Polars. deltalake refused both schemes before any request, so such a side is checked for none. MotherDuck's extension, with `MOTHERDUCK_HOST` and `MOTHERDUCK_USE_TLS=false`, fetched `http://127.0.0.1/extension_version` for `md:sales`. A BigQuery client built with default credentials sent `POST /bigquery/v2/projects/p/jobs` to `BIGQUERY_EMULATOR_HOST` over HTTP. `GOOGLE_BASE_URL` was read with `skip_signature`, and not with a bearer token. PyArrow's Google Cloud Storage file system, under an Iceberg side, sent its bearer token over HTTP to `CLOUD_STORAGE_EMULATOR_ENDPOINT` and to `CLOUD_STORAGE_TESTBENCH_ENDPOINT`, even to a value with no scheme. It did so for a `gs://` table, and for a table on this machine whose metadata names `gs://` files, so every Iceberg side is checked for every object store. PyArrow's S3 file system sent nothing to `AWS_ENDPOINT_URL`, `AWS_ENDPOINT_URL_S3`, or a profile's `endpoint_url`. deltalake refused every `hf://` table before any request, so `HF_ENDPOINT` is left out. deltalake reads every variable with no prefix as an S3 option, so `ENDPOINT_URL` sent a signed list request of an `s3://` table to the store, and its OpenDAL S3 store did the same from `AWS_S3_ENDPOINT`. A service account key that `GOOGLE_SERVICE_ACCOUNT` named, or that `GOOGLE_SERVICE_ACCOUNT_KEY` held, sent a `gs://` table's list request to its `gcs_base_url` over HTTP. With `AWS_ALLOW_INVALID_CERTIFICATES`, `ALLOW_INVALID_CERTIFICATES`, `AZURE_ALLOW_INVALID_CERTIFICATES`, or `GOOGLE_ALLOW_INVALID_CERTIFICATES` on, a proxy with a certificate nothing trusts decrypted deltalake's signed requests. Polars 1.39.3 and 2.1.0 read none of these, and nor did PyArrow's S3 file system. Neither Polars nor PyArrow sent anything to `ENDPOINT`, `ENDPOINT_URL`, or `AWS_S3_ENDPOINT`, so these and `ALLOW_INVALID_CERTIFICATES` are checked on a Delta Lake side only. Polars 1.39.3 and 2.1.0 did send a `gs://` file's request to a service account key's `gcs_base_url`, on a side with `skip_signature`, so a Polars side is checked for it too. A region of `x@127.0.0.1:port/` in `AWS_REGION` or `AWS_DEFAULT_REGION` sent Polars 1.39.3 and 2.1.0, and deltalake, to that address, with a TLS handshake for `s3.x@127.0.0.1:port/.amazonaws.com`. So did the profile's `region` on Polars 2.1.0, and `REGION` and `DEFAULT_REGION`, in any case, on deltalake. Such an `AZURE_STORAGE_ACCOUNT_NAME` sent Polars and deltalake there for an `az://` side. PyArrow refused such a region before any request. Behind a proxy with these switches off, Polars, deltalake, and PyArrow's Azure and Google Cloud Storage file systems sent only `CONNECT host:port` for the side's own host, and kept TLS end to end. PyArrow's S3 file system ignored `HTTPS_PROXY`. A file at an `http://` location went through `HTTP_PROXY` in clear, and the proxy's answer became the tool's. A proxy whose certificate authority `AWS_PROXY_CA_CERTIFICATE` named also decrypted deltalake's requests. `TestEnvironmentEndpoints` in `tests/unit/test_mcp_server.py` holds every variable to each rule on each kind of side, and covers case, scoping, the switches, the service account key, MotherDuck, the profile, the regions, and the account. `tests/integration/test_mcp_environment_endpoints.py` refuses twenty-two real readers with no request or TLS handshake at the store. Its controls show sixteen of them reach it with the rule off: six Polars readers on Polars 1.39.3 and 2.x, eight deltalake readers, and PyArrow under both Iceberg tables.

**Alternative considered:** Strip the variables from `os.environ` as the server starts, and refuse every side of that store. Other options were to refuse to start with any such variable set, to check the STS, metadata, and managed identity endpoints too, to cover proxies, and to move the masking test's store to HTTPS.

**Why rejected:** Stripping changes the process environment under the thread Polars reads it from, a direct Python call would check nothing, and it refuses allowed HTTPS endpoints, so a sovereign Azure cloud loses its only sign-in route. Refusing to start stops a local-only server over an unrelated shell variable. Checking sign-in and metadata endpoints breaks every EC2, ECS, EKS, and AKS operator for no gain, since those endpoints receive only the environment's own credentials. A proxy changes the route and not the host, as the probes show, once the certificate switches are refused. The HTTPS rule keeps a proxy from reading an endpoint's request. A proxy still reads a file at an `http://` location, which carries no credential and is unencrypted on any route, and a proxy whose certificate authority the operator trusts reads everything, as the operator chose. HTTPS trust for the masking test was shown on Linux only, and that test is about masking. Four gaps stay open. The profile can change between the server's read and Polars' read, which matters only when `AWS_CONFIG_FILE` lies under a root. A variable no probe has found yet is not checked. DNS decides the address behind an allowed name. And deltalake reads an all-lowercase `aws_session_token` or `aws_access_key_id`, which `_name_as_read` does not fold, a masking gap for a separate change.

**How to reverse:** Remove the `_refuse_environment_endpoints` call in `_refuse_hosts` in `src/veridelta/mcp_server.py`, with `_ENVIRONMENT_ENDPOINTS`, `_PLAIN_WITHOUT_SCHEME`, `_EMULATOR_SWITCH`, `_CERTIFICATE_SWITCHES`, `_SERVICE_ACCOUNT_FILES`, `_DELTA_LAKE_ONLY`, `_ENVIRONMENT_REGIONS`, `_ACCOUNT_VARIABLE`, `_store`, `_profile`, `_refuse_host_name`, and `_service_account_base_url`. Then delete `TestEnvironmentEndpoints`, `tests/integration/test_mcp_environment_endpoints.py`, the endpoint lines in `tests/unit/conftest.py`, and the environment endpoint, region, and account bullets in `docs/agents.md`.
