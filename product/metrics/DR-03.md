# DR-03: Days from a wrong verdict reported to its fix on PyPI

- **Name.** Days from a wrong verdict reported to its fix on PyPI.
- **The promise it proves.** [UC-02](../USERS.md#uc-02-the-same-verdict-on-every-pull-request): a team that runs the comparison on every pull request can trust the next release to fix what the last one got wrong.
- **Definition and formula.** For each closed issue labeled `bug` that reports a false match or a false mismatch, the days from the issue's creation to the publication on PyPI of the first release that holds its fix. The median over the last ten such issues.
- **Unit and window.** Days, over the last ten wrong-verdict issues.
- **How it is measured.** List the issues, then read the release dates:

  ```bash
  gh issue list --label bug --state closed --json number,title,createdAt,closedAt
  curl -s https://pypi.org/pypi/veridelta/json | python3 -c "import json, sys; releases = json.load(sys.stdin)['releases']; print({version: files[0]['upload_time'] for version, files in releases.items() if files})"
  ```

- **Current value.** Measured 2026-10-06: no issue reports a wrong verdict yet, so there is no value. The open issues on that date are a dependency note and a test run, and neither is a bug.
- **Target, and the reasoning.** Under 7 days. The release path is a pull request and a merge, so a fix can ship the day it lands, and a week leaves room for the Live Warehouses run.
- **What gaming it looks like, and the guardrail against it.** Closing an issue as not a bug, or relabeling it. [GR-02](GR-02.md) counts what is open, and an issue closed without a fix stays in the list by its label.
- **What decision changes when it moves.** Above the target, the next release carries fixes only.
