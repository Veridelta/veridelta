# NS-01: Backends with the same verdict locally and in pushdown

- **Name.** Backends with the same verdict locally and in pushdown.
- **The promise it proves.** UC-01, and every use case that compares two tables where they are stored. The README promises the same verdict in the warehouse as on a laptop.
- **Definition and formula.** The number of pushdown backends whose parity suite passed against the released version, over the six backends the suite covers: DuckDB, Postgres, BigQuery, Databricks, MotherDuck, and Snowflake. A backend counts when every case the suite does not mark `skip_on` for it passed.
- **Unit and window.** Backends, out of six, per release.
- **How it is measured.** DuckDB and Postgres run on every pull request, in the `test-core` and `test-postgres` jobs of `.github/workflows/ci.yml`. The other four run in the Live Warehouses workflow, `.github/workflows/live.yml`, which a maintainer starts by hand. Read the jobs on the release commit, and the latest run of the workflow:

  ```bash
  gh run list --workflow ci.yml --branch main --limit 1 --json conclusion,headSha
  gh run list --workflow live.yml --limit 1 --json conclusion,headSha
  ```

- **Current value.** Measured 2026-10-06, for 0.14.0: 2 of 6. The CI Pipeline passed on the release commit `ebc9fc9`, and the Live Warehouses workflow has never run.
- **Target, and the reasoning.** 6 of 6 before every release. `CONTRIBUTING.md` already makes a green Live Warehouses run the first step of a release. 0.14.0 shipped without it, by the maintainer's decision, and the rule stands.
- **What gaming it looks like, and the guardrail against it.** Marking cases `skip_on` for a backend until it passes. The guardrail to write: the count of `skip_on` markers changes only with its reason in `docs/pushdown.md`, which a test holds.
- **What decision changes when it moves.** A backend below the line blocks the release until its divergence is fixed, or documented in `docs/pushdown.md` with a test that pins it.
